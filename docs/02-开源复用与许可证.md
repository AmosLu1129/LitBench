# 开源复用与许可证策略

## 三条规则

1. **许可证决定「接入方式」，不决定「能不能用」。** 同一个 AGPL 组件，import 进来会传染整个服务，跑在独立容器里则不会。
2. **主仓 MIT，AGPL/GPL 组件一律进程隔离。** 不 import、不 vendor、不 submodule、不打进主镜像。
3. **CI 必须有许可证卡口。** 否则某天一个 `pip install` 就把 MIT 声明废了，而且没人会注意到。

## 为什么 AGPL 在 Web 场景是硬约束

AGPL-3.0 §13：把修改后的程序通过网络提供服务，必须向网络用户提供对应源码。
你的形态正好是 Web 服务 → 直接命中。

- 如果 `import mineru` 或 `import fitz`（PyMuPDF）进同一个进程 → 整个服务被视作 AGPL 作品，**MIT 声明不成立**。
- 如果它们作为独立容器、通过 HTTP/gRPC 调用 → 属于 aggregate（聚合），主仓可保持 MIT。

> 你的项目本来就开源，AGPL 的「提供源码」义务成本极低；问题不是合规难，而是**许可证声明不诚实会被社区抓**。

## 三种接入方式

| 方式 | 适用许可证 | 主仓能否保持 MIT | 例子 |
| --- | --- | --- | --- |
| 依赖（import / package） | MIT、Apache-2.0、BSD | 可以 | Docling、paper-qa、pypdfium2、PDF.js |
| 子进程 / 独立容器 | AGPL、GPL、带附加条款 | 可以（聚合） | MinerU、Marker、pandoc |
| 抄代码 / 改代码 | 只能 MIT / Apache / BSD | 需保留版权与 NOTICE | GPL 系只能看思路重写 |

## 三个最容易踩的坑

1. **PyMuPDF 是 AGPL-3.0。** 它几乎是「PDF 处理」的默认选择，`pip install pymupdf` 写进 Web 服务，MIT 就废了。替代：`pypdfium2`（渲染）+ `pypdf`（结构操作）。
2. **Redis 7.4+ 不再是 BSD**（RSALv2 / SSPLv1）。用 `Valkey`（BSD-3），或者单机直接用 Postgres 做队列。
3. **MinIO 是 AGPL-3.0。** 对象存储直接用云 S3 兼容服务，或 SeaweedFS。

## 可选组件隔离规范

- `compose.yaml` 用 profile：`docker compose --profile ocr up`
- AGPL 组件只通过 HTTP/gRPC 暴露，接口定义在 `server/adapters/`
- 不在 Dockerfile 里把可选组件 `pip install` 进主镜像
- 每个可选组件在 README 单独列许可证与启用方式

## CI 卡口

```yaml
# .github/workflows/license.yml
- run: pip install pip-licenses && pip-licenses --fail-on "GPL;AGPL;SSPL"
- run: npx license-checker --failOn "GPL;AGPL;SSPL"
- run: reuse lint          # SPDX header 检查
```

每个源文件头加 `SPDX-License-Identifier: MIT`。

## 许可证选择：MIT / AGPL / 混合

### 先算暴露面

把 PyMuPDF 换成 `pypdfium2` + `pypdf` 之后，代码层面的 copyleft 只剩：

| 来源 | 性质 | 你本来就要怎么做 |
| --- | --- | --- |
| MinerU | AGPL-3.0 代码 + 权重 | 单独 GPU 容器（重依赖，本来就该隔离） |
| Marker | GPL-3.0 代码 + 权重附加条款 | 可选，不打包 |
| WebPlotDigitizer | AGPL-3.0 | 只参考算法，不拷代码 |
| 其余全部 | MIT / Apache-2.0 / BSD | 直接依赖 |

结论：**「为了复用而改 AGPL」的理由并不成立**——受影响的面积只剩一个你本来就要单独跑的容器。

### 三个方案

| 方案 | 你要付的 | 你得到的 |
| --- | --- | --- |
| A. MIT + 隔离 | 一个 adapter 接口 + 一个可选容器 | 最大采用度；机构无顾虑；可作论文 artifact |
| B. 全仓 AGPL-3.0 | 部分高校 IT / 企业合规禁令；少数贡献者会退 | 可直接 import MinerU；衍生必须开源；挡住闭源 SaaS |
| C. 混合：app AGPL + `schemas/` `mcp/` MIT | 两套许可证要管 | 服务不被闭源，边缘可被集成和贡献 |

### AGPL 能解决什么、不能解决什么

**能：**
- MinerU 可直接 import（但容器化本来更合理）。
- Marker 的 **GPL-3.0 代码**也能进来——AGPL-3.0 §13 明文允许与 GPLv3 作品合并成单一作品。
- Zotero 本身就是 AGPL-3.0，将来做插件没有冲突。

**不能：**
- **模型权重的附加条款**。Marker 的权重有商业收入门槛，这不是换许可证能消化的；只能不分发权重，让用户自己下。
- **数据集与图表版权**。用户上传的 PDF、你要引用的图，与你的代码许可证无关。
- **LLM 服务条款**。BYO key 模式下责任在用户，但 UI 要提示。
- **采用度**。AGPL 不限制使用，只限制分发与「网络提供服务时的源码义务」——个人研究者零负担，但高校 IT 和企业合规部门常有禁令。

### 建议

**C（混合）**：
- 服务的价值在「数据 + 工作流」，最怕被一家公司包走做付费墙，AGPL 正好挡住。
- `schemas/`（领域卡片定义）与 `mcp/`（客户端）保持 MIT，社区才能贡献和集成——这两块最需要外部输入。
- 嫌两套麻烦就退到 A：隔离成本已经接近零。

### 变更时机的成本

MIT 一旦发布，别人可以永久 fork 那一版；之后收紧只保护新功能。**所以「先 MIT，被薅了再改 AGPL」在防白嫖这件事上是假的。** 想防，一开始就定。

### 不搞什么

- 不搞 CLA（降低贡献门槛），用 DCO。
- 不 vendor 任何 copyleft 源码、不做 submodule。

# P0 验证报告：轻量解析档（pdfium）

日期：2026-11-11 · 样本：10 篇 arXiv 开放获取 PDF（`.data/samples/`，不入库）

## 指标怎么定义

用户要的是「按 Fig. 3 找到那张图」，所以指标只有一个：

```
coverage = 能定位到 bbox 的图号数 / 论文里出现的图号数
```

「图号」从 caption 里抽（`Fig. 3` / `FIGURE 3:` / `图3` / `表2`），表题不计入。

不能拿总数糊弄过去。

## 过程中修掉的 4 个真 bug

1. **按基线分行会丢字。** 带下伸部的 g/p/q/y 在 PDF 里的 glyph 底部比基线低 2–3pt，
   按 `bottom` 分行会把它们甩到相邻行：`"Comparison"` → `"Com arison"`，
   `"image"` → `"ima e"`。这种错误肉眼几乎看不出，但会污染所有下游文本。
   改成**按字符垂直中心**分行（中心只偏移约 1pt，行距约 12pt）。

2. **`get_objects()` 在 pypdfium2 5.x 返回生成器**，`len()` 直接抛错；
   而我当时在外面套了 `except: return []`，真实错误被吞成「0 张图」。
   教训：解析器里不要吞异常，宁可炸。

3. **图像对象的 `get_bounds()` 是像素坐标**，不是页面坐标。
   一张 1652×606 的 PNG 返回 `(0,0,1652,606)`；真正的位置在它所属的
   **Form XObject**（type=5）上。必须一路爬到最外层容器取 bounds。
   这个 bug 让 3 篇论文的覆盖率从 100% 掉到 14%。

4. **正文里的 `Figure 3 shows ...` 被误判成 caption**，
   导致同一个图号被重复计数，覆盖率一度出现 107%。
   修法：要求编号后面跟分隔符（`.`/`:`/`—`），或用动词表排除（shows / illustrates …）。

## 剩下的失败模式（视觉抽查确认）

- **通栏图 + 双栏正文混排**：一页里两张图时，第二张的框可能落到正文区。
  根因是我的阅读顺序是「先分栏再自上而下」的近似算法，通栏元素和栏内图混在一起时
  基元归属会串。
- **图与图号跨页/跨栏分离**：caption 在下一页，或图与 caption 各占一栏。
- **表格框线被当成图**：带大量横线的表格区域会被识别成"图区域"。

## 结论

- 轻量档（零模型、192 页约 30 秒）能覆盖大部分单栏/规则双栏论文，
  适合当**默认后端**与**降级路径**。
- 通栏 + 双栏混排是它的能力边界，靠打补丁不划算——这正是 Docling 增强档该上场的地方。
- 下一阶段必须做 A/B：同一批样本上跑 Docling，比 coverage 和耗时，再决定默认值。

## 端到端联调（不经过 HTTP，直接跑通数据链路）

用 SQLite 内存库跑一遍「解析 → 落库 → 检索」：

```
persisted rows: 1114 (blocks=1099, figures=15)

query='FIG. 3'          mode=provenance hits=1
    cite_key=fe39ca-v1-fig3  label=FIG. 3  norm=fig:3
    caption='FIG. 3: Aluminium at low temperature. Left: abso...'

query='Figure 9'        mode=provenance hits=0     ← 该论文没有 Fig. 9，确定性返回 0
query='Simulated shock'  mode=semantic   hits=15    ← 降级语义检索
```

这组结果验证了三件事：解析产物能落进 6 张表、`cite_key` 稳定且可回查、
出处检索**不会**在找不到时退化成「给你几个相似的」。

## 修订：加了「文字密度否决」之后（2026-11-11 晚）

前端截图暴露出一个问题：**有三分之一的缩略图是正文而不是图**。
原因是有些 PDF 把文字也画成 path（Type3 字体、文字底纹），
caption 锚点生长时会撞上一片装饰路径，把整段正文认成图。

加了否决规则：候选框内被正文行覆盖的面积 > 30% 就判为正文，拒绝该框。

| 指标 | 加否决前 | 加否决后 |
| --- | ---: | ---: |
| 定位成功的图 | 66 / 77 | **53 / 77** |
| coverage | 86% | **69%** |
| 肉眼可见的「正文缩略图」 | 约 1/3 | 仍有约 15% |

**这是一个刻意的取舍：宁可少给，也不给错的。**
出处检索的价值在于确定性——用户输入「Fig. 3」却拿到一段正文，比拿不到更伤信任。

剩下的 15% 不建议继续打补丁：它来自「通栏图 + 双栏正文」和「文字即路径」两类版面，
本质需要版面模型，也就是 Docling 增强档。

## Docling 状态（未完成端到端验证）

- 安装成功：`docling 2.150.0` + `torch 2.15.0+cpu`（Python 3.14 有 wheel）。
- **坑 1：Windows 中文路径。** `docling-parse` 的 C++ 层打不开含非 ASCII 的路径
  （报错为 `...\agent??\...`）。项目目录带中文时，本地只能用目录联接绕开：
  `mklink /J C:\litbench D:\your\中文目录\litbench`。容器内是 Linux 路径，无此问题。
- **坑 2：首次运行要下模型**（layout / tableformer），默认走 HuggingFace；
  国内网络需 `HF_ENDPOINT=https://hf-mirror.com`，否则 `snapshot_download` 直接超时。
- 适配器代码已完整（含字段映射表），但**本地未跑通**（模型下载未完成），
  因此本报告不包含 Docling 的任何数字。

### 0.6 压缩后容易踩的坑

- **环境变量名**：pydantic-settings 字段是 `auth_enabled`，环境变量必须写 **`AUTH_ENABLED=1`**，
  不是 `LITBENCH_AUTH`（踩过）。
- **dev SQLite 没有 alembic 版本表**：新迁移不能直接 `alembic upgrade`，
  要照迁移文件手写同样 DDL，或重建 dev 库；`test_migration_matches_models.py` 只校验模型与迁移文件一致。
  **0014 已手工应用**（4 张新表 + 3 个 owner 字段 + 索引；脚本 `.data/tmp/apply_0014.py` 可重复执行）；
  **0015 已手工应用**（`paper` 的 entry_type + thesis_school/degree/place；脚本
  `.data/tmp/apply_0015.py` 可重复执行）；**0016 已手工应用**（`claim_revision` 表 + 索引；
  脚本 `.data/tmp/apply_0016.py`），后续迁移 0017+ 仍需同样处理。
- **认证打开时**：MCP/脚本直接调 `/api/*` 会 401；两种解法：
  (a) 部署侧设 API `INTERNAL_API_TOKEN` 与 MCP `LITBENCH_MCP_API_TOKEN` 为同一个随机串；
  (b) 临时 `AUTH_ENABLED=0` 起 API（仅本机开发）。令牌为空 = 不启用，服务端不会放宽。
- **Vite preview 走 `/api` 代理**：cookie 在 4173 同源下正常；不要直接用 8000 调前端接口。
- **Docker 部署（本机）**：没有 Docker Desktop；真跑用的是 WSL2 Ubuntu 里的 docker.io +
  docker-compose-v2（`docker compose up --build -d`，端口 18000/18080），并且 daemon 需要
  registry mirror（Docker Hub 直连超时）。三个已修坑：容器缺 `greenlet`
  （`sqlalchemy[asyncio]`）、迁移里 boolean 默认值必须是 true/false、`/api/ready` 必须免登录
  （否则 HEALTHCHECK 401 → api unhealthy）。详见 `docs/15` §12.30。
- **Windows 编码/临时目录**：npm build 需设 `TEMP/TMP` 到 `.data/tmp/esbuild`；GBK 控制台读中文
  要 `sys.stdout.reconfigure(encoding='utf-8')`。
- **BM25 / 查询改写 / 表格 LaTeX（M9 新增）**：BM25 是**词面**排序；中文查询会先用 chat
  模型改写英文术语（M9.1b-lite，只中文触发、有缓存、失败回退），但**仍不是 embedding
  向量召回**；图/文献候选上限 5000/2000。表格 LaTeX 的 Unicode 数学字符已在
  转换器里归一，xelatex 若报 MiKTeX「未检查更新」非零退出但 PDF 可能已生成（别只看 exit code；
  先看 `.pdf` 是否存在）。
- **CSL 引擎（M8 新增）**：`engine=csl` 依赖 **pandoc**（`PANDOC_PATH` → 项目内
  `scripts/get_pandoc.py` 装的 `.data/tools/pandoc/*/` → PATH 依次找；项目内优先，
  避免系统旧版 pandoc 2.x）；没装 → 503，不假装成功。**不要换回 citeproc-py**：
  实测它会吞掉 GB/T 的 `[J]`/`[D]`（无 DOI/URL 时整组被抑制）、IEEE 引号内标点不同、
  APA 参考文献表不排序（对比见 `docs/15` §12.42）。pandoc 只作子进程调用（GPL-2.0），
  命令带 `--sandbox`（不读正文/元数据里引用的任意资源）。CSL 输出是**纯文本**、
  只渲染参考文献表；Docker 镜像本机未完成重建（下载网络超时，已加镜像回退/超时，
  留部署补验，见 `docs/15` §12.46）。
- **Word/PDF 导出（M8 新增）**：`.docx` 依赖 pandoc，`.pdf` 还依赖 **typst**
  （`TYPST_PATH` → 项目内 `.data/tools/typst/*/` → PATH）；**不要改用 xelatex**——API
  进程（Python subprocess）拉起 xelatex 时 MiKTeX 25 写不了自己的日志目录，直接失败
  且不产 PDF（本机实测）。导出内容只是 claim 正文 + CSL 参考文献，不含图表排版/学校
  模板；支持 `\cite{key}` 与 `[@key; @key2]` 改写，解析不了 → 422；超过 500 张卡片
  明确 422（不静默截断）；`paper_ids` 里未引用的文献也会进参考文献表（`nocite`）。
  导出临时目录在 storage_dir 下，pandoc 带 `--sandbox`。
- **元数据补全（M8 新增）**：`metadata/lookup` 会真的请求 `api.crossref.org` /
  `export.arxiv.org`（`METADATA_TIMEOUT_S` 默认 15s，`CROSSREF_MAILTO` 只进
  User-Agent）；没网/被墙 → 502，不影响本地功能。`apply` 默认只填空白字段，
  覆盖已有值必须 `overwrite=true`（手滑覆盖人工/Zotero 元数据没有撤销，先看 diff）；
  **不写 Zotero**，写的是 LitBench 的 `paper` 表；共享文献对非 owner 只读。
- **写作大纲 / 交叉检查（M8 新增）**：`/api/writing/outline` 是**只读派生**，不改
  claim；图表检查只做词面编号比对（`图 3` vs 证据 `图 4`），不是语义判断；子图
  `图 3(a)` 与 `图 3` 会被当成不同编号、可能提示不一致（保守报出）。章节归章依赖
  `thesis._SECTION_ALIASES`，未知 section 作为额外章节追加、不丢内容。
- **xelatex 验收（M9.3c 踩到）**：MiKTeX 25 把「未检查更新」记成 major issue；
  **从 Python `subprocess` 拉起的 xelatex 会被判失败且不产 PDF**，由 agent/工具侧
  shell（PowerShell/bash）直接启动则正常（也会打印 major issue，但退出 0 且 PDF 正常）。
  所以编译这步交给 agent 做，不要包进 Python 脚本。`scripts/verify_table_latex.py`
  prepare 出 `.tex` + `compile.ps1`/`compile.sh`，agent 执行编译，report 解析
  Overfull/页数/LaTeX 错误并给验收退出码。`table_latex` 默认 `width=auto`
  （宽表 p 列换行），要旧的纯 `l` 列时接口传 `?width=plain`。
- **Docling 必须从 ASCII 路径跑（M9.3b 踩到）**：`docling_parse` 是 C++ 扩展，路径里带中文
  （`<中文工作目录>\...`）会报 `filename does not exists: ...glyphs//standard/additional.dat`，
  不是模型没下完。从目录联接 `C:\litbench` 启动、并设 `HF_HOME=C:\litbench\.hf-cache` 即可
  （505MB 模型已缓存）。`mineru-kit` 同理，adapter 会把 PDF 先复制到 ASCII 工作目录。
  MinerU `standard` 档另需约 2GB 模型（`mineru-kit models download --tier standard`，已下到
  `.data/mineru-home`，`mineru-kit models verify` 应显示正常）；档位可从 middle_json 的
  `extensions.mineru.tier` 核对。
- **桌面的预览 zip 已过期**：`<Desktop>\LitBench-Preview-2026-11-13.zip` 是 11-13 的版本，
  不含 References / M5 真机 / 团队共享；需要重新打包时按旧流程重做。

## 1. 项目定位（一句话与三条取舍）

**LitBench 是「文献证据中间层」**：把文献里的段落、表、图变成结构化、可检索、可溯源、
能直接进写作流程的资产。它不跟 Zotero 抢「读」，做的是从「读过」到「写出带正确引用的稿子」
之间那段手工搬运。

已定下的三个产品判断（写进 ADR-0001，不要在后续开发中推翻）：

1. **不做通用 AI 读文献工具**。单篇总结、多文档问答已被商品化（例如 MIT 许可的
   Open Research Assistant for Zotero 已覆盖），这些不是壁垒。
2. **图/表是一等公民**。工作台是双轴：按文献（知道找哪篇）+ 按主题（不知道找哪篇）。
   主数据永远是「图 + caption + 上下文 + 出处 + 许可」，**不试图理解图的内容**
   （VLM 描述只作可选辅助字段，会产生幻觉）。
3. **误报可接受，但必须能被纠正**。最终形态是多智能体协作，agent 是主纠错门限，
   所以纠错通道（review）比把解析精度再提几个点更重要。

## 5. 数据模型（23 张表）

> 迁移一致性由 `tests/test_migration_matches_models.py` 保证：它会**按顺序执行所有迁移**
> （用假的 alembic.op 记录），再和 `Base.metadata` 逐表/逐列/逐索引比对。加迁移不会静默漂移。

### paper（一篇文献，不含具体文件）

`id`(32) `doi` `arxiv_id` `cite_key` `title` `title_norm` `authors_json`(JSON) `year`
`venue` `volume` `issue` `pages` `entry_type`(journal|conference|preprint|thesis|book|report|other，默认 journal)
`thesis_school` `thesis_degree` `thesis_place`（迁移 0015，学位论文 `[D]` 著录用）
`status`(new|parsed|needs_ocr|failed) `created_at`

### paper_version（一个具体 PDF 文件）

`id` `paper_id`(FK) `kind`(uploaded|preprint|published|correction) `venue` `year` `doi`
`arxiv_id` `file_sha256`(**唯一**) `file_path` `page_count` `parser` `parser_version`
`parsed_at` **`text_quality`（0–1 文字层质量分）** **`text_quality_flags_json`（指标明细/双 OCR 统计）**
`created_at`

> 为什么图和 block 挂 version 而不是 paper：arXiv v1 的 Fig.3 和正式版 Fig.3 常常不是同一张图，
> 引用必须指向实际读到的那一版。

### block（版面块，唯一真值）

`id` `paper_version_id` `page` `bbox_json`([x0,y0,x1,y1]，左上原点、PDF 点)
`type`(text|title|section|table|figure|caption|formula|ref|header|footer)
`text` `order_idx` `parent_id` `engine` `conf`
索引：`(paper_version_id,page,order_idx)`

### figure（图，一等公民）

`id` `paper_version_id` `block_id` `page` `bbox_json` `image_path` `thumb_path`
`label_raw`(原文写法 "Fig. 3") `label_norm`("fig:3"、"fig:s3"、"fig:3a") `label_num` `sublabel`
`caption` `figure_type` `license_hint`(reuse|permission|redraw|unknown)
`cite_key`(唯一，形如 `2755f7-v1-fig3`)

**图号校核字段（迁移 0003）**：
- `label_source`：`text | rule_repair | rule_inherit | rule_infer | ocr | ocr_consensus |
  ocr_cross_conflict | ocr_cross_unresolved | review | none`
- `label_confidence`：0–1；< 0.6 在界面上打「待确认」
- `group_key`：同一系列子图的组（`p{page}-g{n}` 或 `manual-xxxx`）
- `sublabel`：子图字母 a/b/c（复用已有列）

**定位纠错字段**：`review_status`(pending|ok|wrong) `review_note` `bbox_override_json`
`reviewed_by` `reviewed_at`

**用户增删字段（迁移 0004）**：
- `origin`：`parser`（解析器产出）/ `manual`（用户在原文里框选添加）
- `deleted_at`：软删除时间戳；所有检索 / 列表 / 计数 / 详情 / 图片接口都过滤它。
  重解析时按 cite_key 把删除标记压回新解析结果（删掉的图不会复活），
  manual 图按原字段回填（用户加的图不会丢）。

> 两个都要存：`label_raw` 写进论文，`label_norm` 用于检索。只留一个必出问题。
> **图号校核（label_*）和定位纠错（review_*）是两条独立通道**：前者说「这张图叫什么」，
> 后者说「框对吗」。`label_source=ocr_cross_unresolved` 时 `label_norm` 故意为空
> （否则会退化成 fig:4），只保留 `label_raw` 给 review。
> `bbox_override_json` 若有值，API 返回的 `bbox` 就用它（overlay 立刻变对；缩略图待重渲染）。

### tab（表）

`id` `paper_version_id` `block_id` `page` `label_raw` `label_norm` `html` `cells_json`
`caption` `quality`(structured|image)

### job（任务）

`id` `kind`(parse|extract|export) `paper_version_id` `status`(queued|running|done|failed)
`progress` `error` `attempts` `payload_json` `created_at` `started_at` `finished_at`

**不变量**：AI 产出必须带证据。`summary` 已经由 `litbench/evidence.py` 在落库前强制
（`evidence_block_ids` 非空且必须属于本节）；card_field / claim / cite_anchor 等 P2 产出
仍待同样的服务端校验。

### collection / paper_collection / import_run（迁移 0005，M1 知识库）

- `collection`：`id` `name` `parent_id`(self FK) `sort_order` `source`(manual|zotero)
  `zotero_key`(unique) `created_at`。Zotero 集合按 key 只读镜像。
- `paper_collection`：`paper_id` + `collection_id`（联合主键），一篇可属多个集合。
- `import_run`：`id` `source`(json|sqlite|api) `started_at` `finished_at` `stats_json` `error`。
- `paper` 新列：`abstract` `tags_json` `reading_status` `zotero_item_key`(unique)
  `metadata_source`(upload|zotero|arxiv) `imported_at`；**2026-11-12 工作台改版**再加
  `note`(Text，用户备注，不进检索/AI) 与 `favorite`(Boolean，收藏夹虚拟视图)。
- 导入语义（D1 只读）：集合/条目按 Zotero key 幂等 upsert；手动集合不会被同步删；
  `POST /api/import/zotero/file` 支持上传 Zotero 导出 JSON。详见 `docs/15`。

### summary / summary_revision（迁移 0006，M2a 章节摘要）

- `summary`：`id` `paper_version_id`(FK) `section_key` `section_title` `level` `content`
  `key_points_json` `evidence_block_ids_json`（**必须非空，落库前由 `evidence.py` 校验**）
  `source`(agent|human_edited) `provider` `model` `prompt_version` `status`(draft|published)
  `tokens_in/out` `cost` `auto_accepted` `human_locked` `created_at` `updated_at` `edited_by` `edited_at`；
  唯一约束 `(paper_version_id, section_key)`。
- `summary_revision`：`summary_id` + 旧内容快照 + `reason`(generated|edited|regenerated|restored)，
  生成/编辑/回滚前各压一份，可回滚。
- 语义（D3）：mock/真实 provider 生成 → 证据校验 → 置信度 ≥ 0.9 自动接受为 published；
  用户编辑 → human_edited + human_locked，自动生成永不覆盖（除非显式 force）；详见 `docs/15` §12。
- **整篇速览（2026-11-12 晚）**：同一张表里用 `section_key="__paper__"` 存整篇总结
  （`level=0`、`section_title="整篇速览"`），证据/锁定/回滚复用同一套逻辑；章节摘要列表接口会过滤它。

### claim / claim_revision（M5 写作卡片；历史 2026-11-15 小修）

- `claim`：`id` `paper_id`(FK) `paper_version_id` `text` `section` `status`(draft|approved)
  `source`(human|agent) `evidence_json`（≥1 条、必须落在同一已解析版本）`tags_json`
  `order_idx` `created_by` `owner_user_id` `created_at` `updated_at`。
- `claim_revision`（迁移 0016）：`claim_id`(FK CASCADE) + 旧状态快照（text/section/status/
  source/evidence_json/tags_json/order_idx/paper_version_id）+ `reason`(edited|restored) +
  `edited_by` + `created_at`；每次内容真正变化前压一份，恢复前也压当前状态，可回滚。

### figure_proposal（迁移 0007，M3 图提取 AI 纠错）

- `figure_proposal`：`id` `figure_id`(FK) `paper_version_id`(FK) `kind` `proposed_json`（图号/图注/
  裁框建议 + 校验注记）`evidence_json` `confidence` `status`
  (pending|accepted|rejected|superseded|no_change) `provider` `model` `prompt_version`
  `mode`(vision|text) `tokens_in/out` `cost` `latency_ms` `decided_at/by/reason`。
- 语义：AI 只产出建议；**采纳才写 figure 正式字段**（图号→`label_source=review`、图注直接替换、
  裁框问题→`review_status=wrong`，不自动改 bbox）；拒绝也留记录；同图只保留最新 pending；
  检查后无问题记 `no_change`，不进待审队列。详见 `docs/15` §12.10。

**检索判路规则**（`litbench/search.py::classify`）：

- 命中文档标识（DOI / arXiv / Zotero citekey / 作者+年份 / 图号）→ `provenance`（确定性，0 条就是 0 条）

### 8.1 pdfium 轻量档（默认）

文件：`adapters/pdfium_parser.py`。零模型、192 页约 30 秒（实测 10 篇 4.5 秒）。

实现里三个踩过坑、写死在代码里的决定：

1. **按字符垂直中心分行**，不按基线。带下伸部的 g/p/q/y 的 glyph 底部比基线低 2–3pt，
   按 bottom 分行会随机丢字母（`"Comparison"` → `"Com arison"`），肉眼极难发现却污染所有下游文本。
2. **图不从 image 对象来**。arXiv 大量图是 matplotlib 矢量图（一篇几千条 path）。
   把 path(2) 与 image(3) 一起当绘图基元，按网格掩膜聚类。
3. **以 caption 为锚点生长图区域**，而不是先检图再配对。每个图号必须对应一个 bbox。

坐标处理：图像对象的 `get_bounds()` 是**像素坐标**，真实位置在所属 Form XObject 上，
必须**爬到最外层容器**取 bounds；裁剪图用「整页渲染一次 + PIL 按 bbox 裁剪」
（不要用 `page.render(crop=...)`，5.x 的 crop 语义与直觉不符，实测给 150×150 返回 724×1084）。

> **坐标原点（2026-11-11 修，重要）**：pdfium 的 `charbox` / `get_bounds` 全是 **PDF 原生
> 左下原点**（y 向上），而 PIL 裁剪、PDF.js overlay、golden set 全按**左上原点**用。
> 之前没做转换，结果是每张缩略图都从页面垂直镜像的位置裁出来——**「15% 缩略图是正文」
> 的真因其实是这个**（翻过来裁就是真图，见 `.data/tmp/coords-real-*.png`）。
> 现在在 parser 出口统一 `_to_top_left()`；`_merge_caption` 的「下一行」方向也按原生坐标修正了。

**扫描页（整页就是一张位图）单独走一条路**（2026-11-11 加）：arXiv 论文的插图是页内小对象，
所以「面积 >90% 的对象当底纹丢掉」是对的；但影印课本每页就是一张 100% 覆盖的位图，
原来这条规则会把整页图全丢掉（figures=0）。现在的判据与做法：

- `_is_scanned_page()`：存在一张覆盖 ≥90% 页面的 image 对象 → 扫描页；
- 扫描页不走绘图基元生长，改 `_resolve_scanned_box()`：**caption 为锚点，找它上/下侧
  更大的空白带**，空白带边界由正文行（≥12 字或 ≥半页宽）决定，再夹掉页边 4% 的页眉页脚；
- 三道否决：带内文字覆盖率 >20% / 带内有章节编号行（"7.7 热管简介"）/ 带高 <50pt 或 >92% 页高。

过滤规则（避免把正文/底纹当图）：

- 基元：宽或高 < 3pt 丢掉（表格线）；面积 > 页面 50% 丢掉（背景）；水平/垂直贯穿线丢掉。
- 图区域：面积 < 页面 1% 丢掉；高度 > 页高 90% 丢掉；**框内正文行覆盖面积 > 30% 丢掉**。

caption 合并（`_merge_caption`）：按**几何**找下一行（同栏左边界 ±18pt、行间距 ≤3.5pt），
不依赖阅读顺序（阅读顺序会把页脚、邻栏首行插进来）。

### 8.3 Docling 增强档

文件：`adapters/docling_adapter.py`。A/B 实测（`docs/08`）：

| 后端 | 论文 | 图号覆盖 | 表格 | caption 均长 | 耗时 |
| --- | --- | ---: | ---: | ---: | ---: |
| pdfium | 12736（22 页） | 93% | 0 | 97 字 | 0.6 s |
| docling | 12736（22 页） | 100% | 4 | 611 字 | 62.8 s |
| pdfium | 12840（15 页） | 100% | 0 | 82 字 | 0.1 s |
| docling | 12840（15 页） | 100% | 1 | 281 字 | 25.9 s |

结论：**默认 pdfium**；Docling 按需开启。它的独有优势是**表格**和**整段 caption**，
代价是 100–400 倍耗时。

Docling 适配器两个已修的关键点：

- **bbox 是 BOTTOMLEFT 原点**：换算必须用页高（`doc.pages[n].size.height`），
  取负号会得到负数坐标、overlay 画到页面外。
- caption 优先用 `item.caption_text(doc)`（Docling 自带的 caption 链接），
  其次 `captions` 里 RefItem 的 `#/texts/N` 解析，最后才退回几何绑定。

### 8.4 按需升级（默认开启）

worker 解析完会跑一次判据（`escalate.py::find_weakness`），**明显不够就自动再排一个增强档 job**。
默认档不变（还是秒级 pdfium），只有被判弱的那篇才花那 40–60 秒。

| 判据 | 触发条件 | 为什么是这条 |
| --- | --- | --- |
| `unanchored_captions` | 图注里出现 N 个图号，实际只定位到 < N 张图 | 轻量档最主要的失败模式，而且**可量化** |
| `short_captions` | ≥2 张图、图注平均 < 40 字 | caption 只抓到「Figure 3.」几个字，说明版面没读懂 |

以下情况不升级：扫描件（没有文字层，那是 OCR 的事）、已经是增强档（**只升一级，不循环**）、
同版本已有增强档 job（重复上传不重复烧 60 秒）、没装 docling（排一个注定失败的 job 没意义）。
判据和统计都在 `escalate.py`，`ParsedDocument` 是纯输入，好单测、好调阈值。

本机 10 篇样本的实测：**7/10 会被判弱**（3 篇缺 2–11 个锚定，2 篇 0 张图）。
对 12886（17 页）真跑一遍：pdfium 是 `3 个图号 / 0 张图 / 0 表`，Docling 是
`4 张图（caption 368–505 字）+ 7 个结构化表格`，耗时 **45 秒**。

两个只在真跑时暴露的问题（都已修）：

- **Docling 不给像素**，只给 `(page, bbox)`，升级后图卡片会全部变成「无图片」。
  现在两个后端共用 `adapters/render.py`（整页渲染一次 + PIL 裁剪）补缩略图。
- 表格的 `caption` 曾经取成整张表的 markdown（`| Benchmark | ...`），因为它走了
  `item.text` → `export_to_markdown` 的兜底。表题必须用 Docling 的 caption 链接。

配置：`ESCALATE_BACKEND=docling|mineru|（空字符串=关闭）`、`ESCALATE_MIN_MISSING=1`、
`ESCALATE_MIN_CAPTION_CHARS=40`。

### 8.5 MinerU（2026-11-11 真实接入，不再是桩）

> 许可证纪律：MinerU 是 AGPL-3.0，**主进程绝不 import**。这里只通过独立 venv 里的
> `mineru-kit` CLI 子进程调用，主镜像里既没有它的代码也没有依赖（`THIRD_PARTY.md` 有登记）。

- **安装**：`C:\mineru-env\`（独立 venv，Python 3.14.6，`mineru==4.2.0`，约 786MB）。
  不装进项目 `.venv` 的两个原因：①AGPL 隔离；②MinerU 的 C++ 解析层打不开非 ASCII 路径。
- **调用**：`adapters/mineru_adapter.py::MineruParser`
  ```
  mineru-kit parse <ascii输入.pdf> -o <out> --format middle_json --pages all --tier flash
  ```
  输入先按 sha256 复制到 `MINERU_WORKDIR/input/`（ASCII），输出读 `docvortex.middle` v2 JSON；
  子进程环境钉住 `MINERU_HOME`、`MINERU_MODEL_SOURCE=modelscope`、`TEMP/TMP=MINERU_WORKDIR/tmp`
  （DSH 沙箱里子进程只能写工作区内路径，`C:\mineru-work`、`%TEMP%` 都会被拒）。
- **模型**：`C:\litbench\.data\mineru-home\models`（`config.yaml` 的 `model.base_dir` 指过去），
  flash 档只用 ONNX 小模型（CPU/GPU 均可，本机 RTX 4070 Laptop 走 DirectML）；
  首个调用会从 ModelScope 拉权重。**权重不进仓库**。
- **输出映射**（`to_parsed_document`）：
  - bbox 是**归一化 [0,1] 左上原点**，乘页面宽高（本书 514.49×728.30 pt）→ PDF 点；
  - 图块类型：`image` / `chart`（都是图，`chart` 是折线/曲面类示意图）；
  - **图注/表题挂在图块自己的 `content` 里**（`image_caption` / `chart_caption` /
    `table_caption` 子块）——适配器递归取出来挂到 figure/table 行；不读子块等于把整本书的
    图注全丢掉（整章 104 张图只有 6 张能对上号就是这么来的）；
  - 无文字层判断：`text_layer = 全文块字数 > 100`。
- **页级触发**（`workers/run.py::_maybe_ocr`）：pdfium 解析完 `text_layer=False` →
  自动排 `job(backend=OCR_BACKEND, payload={"ocr":True,"ocr_from":...})`；
  只排一级、同版本不重复排、后端不可用就停在 `needs_ocr` 并把原因写进日志。
- **实测吞吐**（整章，含缩略图裁剪）：**27–33 秒/本**（29–47 页，约 0.7–0.8 秒/页）。
- **档位**：`flash`（默认，ONNX 小模型）**不产独立 caption 块、表格是 markdown 文本**；
  需要结构化表格/独立 caption 时走 Docling，或试 `standard`（未实测）。
- 故障处理：CLI 不存在 / 超时 / 非零退出 → `ParserError`，job 失败可见；缩略图裁剪失败
  不影响整篇解析（图仍入库，只是没缩略图）。
- 已知限制与选型对比见 **`docs/11-OCR路径对比.md`**；真实语料验收见 `docs/12`。

### 8.6 双 OCR 交叉校核 + 文本层质量（2026-11-12，阶段 2）

> 用户要求：文字层质量低/困惑度高时降权文字层，**宁可相信两套 OCR 的交叉结果**。
> 完整方案与阶段记录见 **`docs/14-图号校核与文本层置信度.md`**。

- **第二套 OCR**：RapidOCR 3.10（Apache-2.0，可进主镜像）+ **PP-OCRv4 mobile**（onnxruntime）；
  与 MinerU 的 PP-OCRv6 small 是不同版本/权重，但同属 PaddleOCR 家族，独立性有限。
- **只裁图注小图**：MinerU 输出里图注子块有精确 bbox（`ParsedFigure.caption_bbox`），
  第二套只识别这一小块（200dpi），不整页重跑；书 03 只校核 39/104 张（无号/字母段/低置信），20s。
- **判定**（`litbench/ocr_cross.py`）：
  - 两套原始编号字面量一致且可归一 → `ocr_consensus`（0.95）；
  - 主 OCR 没读到、第二套读到 → `ocr`（0.8）；
  - 字面量不同 → `ocr_cross_conflict`（0.35，进 review）；
  - 两套都读成「图 4.e.1」这类字母段 → `ocr_cross_unresolved`（0.35，**不硬改成 4.5.1**；
    persist 不写 label_norm，只留 label_raw 给 review）。
- **文字层书融合**（`merge_text_layer`）：书 01/02 质量低/图注有噪声时再跑一套 MinerU OCR，
  按页/bbox 匹配；文字层错号/无号以 OCR 为准，一致则升 consensus。书 01 的「图 162」
  被修正为 图10-2/图10-3；书 02 从 31 有号提到 54。
- **成本**：书 01 整链路约 163s（Docling 110 + MinerU 30 + 局部校核 20），
  书 02 约 131s；纯 OCR 书 35–53s。配置项 `OCR_CROSS_ENABLED` / `OCR_CROSS_DPI` /
  `TEXT_QUALITY_MIN`（见 `.env.example`）。

### 状态与交互

- **双轴**：点侧栏文献 → 按文献看图；点「全部图」/直接搜索 → 全部或检索结果。
- **搜索**：300ms 防抖；空查询走 browse。
- **详情**：点卡片打开；`Esc` 关闭。
- **纠错**：详情面板两个按钮「定位正确 / 定位错了」→ `POST /review`；卡片上显示「已确认 / 已判错」标记。
- **原文查看**：详情面板「在原文中查看（第 N 页）」→ PDF.js 渲染该页，红框标出 bbox，
  `←/→` 翻页，`Esc` 关闭。按 `devicePixelRatio` 放大 canvas。
- **拖框修正**：在原文页面上直接拖一个新框 → `POST /review {verdict:"wrong", bbox}`。
  后端按新框**重裁缩略图**并给 `image_url` 加 `?v=<reviewed_at>`（图片响应有 24h 缓存，
  不带版本号用户修完看到的还是旧图），overlay / 详情 / 卡片网格一起刷新。
  坐标换算：CSS px ÷ `viewport.scale` = PDF 点，再夹到页面范围内；拖动时有蓝色虚线预览。
- **章节摘要（M2a）**：点文献 → 子页签「章节摘要」→ 左章节树（状态：无摘要/草稿/已发布/
  人工/分组；`block_count=0` 是纯父节点不可生成）→ 右摘要详情（正文/要点/证据块）→
  点证据打开原文对应页并高亮 bbox；可编辑（保存后 human_edited + 锁定）、发布、重新生成
  （force，二次确认，人工锁定跳过）、看历史版本/回滚。生成失败以 banner 列出章节+原因。
- **AI 速览（整篇一键总结，2026-11-12 晚）**：文献页子页签「AI 速览」→ 空态点「AI 一键总结」
  （整篇一次模型调用，约 12–30s；材料=摘要+章节大纲+引言/结论证据块）→ 正文/要点/证据块，
  证据可点回原文；支持编辑（锁定）、发布、重新生成、历史版本回滚。接口
  `GET/POST /api/papers/{id}/summary`；整篇速览存在同一张 `summary` 表（`section_key="__paper__"`）。
- **AI 图纠错（建议队列，2026-11-12 晚）**：三个入口——① 图详情「AI 纠错：AI 检查这张图」，
  内联显示「当前值 → 建议值」，采纳/忽略；② 顶栏「AI 建议 N」抽屉：全部待审建议（缩略图、
  视觉/文字模式、置信度、逐条处理、「采纳高置信 ≥0.9」批量）；③ 文献图表页「AI 修图（N）」
  与待确认队列页「AI 复核这 N 张」：串行最多 8 张、按钮显示进度。**建议不自动改图**：
  采纳才写图号/图注，裁框问题只标「定位错误」（框仍需人工在原文里拖）。接口见 §API 表。
- **工作台改版（2026-11-12 晚）**：
  - 侧栏「知识库 → 管理」进入**知识库操作台**：左分组树（全部/★收藏夹/手动分组与子组，改名/删组/

### 10.1 回归度量：golden set 导出与回放

**这是「改解析器之前先量一下」的那个工具。** 用法：

```powershell
# 1. 先在界面/API 里复核几十张图（定位正确 / 定位错了，可带修正框）
# 2. 导出（直连库，不用起 API）
python scripts\export_golden.py -o .data\golden.json
# 3. 回放：默认按每条记录自己的后端重放（幂等性检查）
python scripts\replay_golden.py .data\golden.json -o .data\replay-current.json
# 4. 关键一步：强制用基线后端重放，量出「不升级的代价」
python scripts\replay_golden.py .data\golden.json --backend pdfium
```

判分规则（`litbench/golden.py`）：

- **期望有框**：`ok` 条目，或 `wrong` 但人工给了修正框（修正框是最值钱的正样本）。
  新解析仍锚定同一图号且 IoU ≥ 0.5 → `pass`；给了修正框的用 **0.9** 阈值（人工精确到框，不能用 0.5 放水）。
- **期望没框**：`wrong` 且没给修正框。仍落回同一错框 → `still_wrong`；换框或干脆没有 → `fixed`。

本机实测（6 条 golden：4 ok + 2 wrong，其中 1 条带修正框）：

| 回放方式 | recall | 平均 IoU | 说明 |
| --- | ---: | ---: | --- |
| 按条目原后端（docling + pdfium） | **0.80** | 0.96 | 4/5；唯一没过的是「人工修过框」那条，解析器还没学会复现人工修正 |
| `--backend pdfium`（基线） | **0.20** | 0.36 | 1/5；Docling 才找到的 3 张图全部漏掉 —— 这就是按需升级的收益 |

注意：**回放 docling 也要从 ASCII 路径启动**（同 §11 第 1 条），脚本会在报错时提示。

顺带修了一个由此暴露的 bug：`persist` 的「先删后插」会把人工复核结果一起删掉。
现在按 `cite_key` 在重解析前快照、插入后回填——**解析可以重跑，人工判断不能丢**。

## 11. 环境坑清单（全部实际踩过，按出现频率排序）

1. **中文路径杀死 Docling。** `docling-parse` 的 C++ 层打不开含非 ASCII 的路径，
   报 `filename does not exists: ...\agent??\...`。项目在 `<中文工作目录>\...`，
   所以本地跑 Docling 必须建目录联接：
   ```powershell
   cmd /c mklink /J C:\litbench "<repo>"
   C:\litbench\.venv\Scripts\python.exe C:\litbench\scripts\probe_docling.py
   ```
   容器里是 Linux 路径，无此问题。
2. **HF 模型下载。** 直连 HuggingFace 超时；设 `HF_ENDPOINT=https://hf-mirror.com`，
   并把 `HF_HOME` 指到可写目录（本机用 `C:\litbench\.hf-cache`，已下 505MB）。
   默认缓存目录 `C:\Users\<user>\.cache\huggingface` 曾报 PermissionError。
3. **SSL 证书。** Windows 系统证书库缺中间证书，`Invoke-WebRequest` / curl 默认失败。
   解法：Python 里用 `certifi` 建 `ssl.create_default_context(cafile=certifi.where())`
   （已写进 `scripts/fetch_samples.py`）；或用 `curl.exe --ssl-no-revoke`。
4. **SQLite 大事务临时文件。** 本机 `tempfile.gettempdir()` 返回 `<中文工作目录>`（中文路径），
   大事务一溢出就 `unable to open database file`，且只在数据量大时出现。
   已在 `db.py` 对 sqlite URL 加 `PRAGMA journal_mode=WAL; temp_store=MEMORY; synchronous=OFF`。
5. **esbuild 临时目录。** `npm run build` 偶发 `Access is denied` 删除系统临时文件。
   解法：构建前 `$env:TEMP="$p\.data\tmp"; $env:TMP=$env:TEMP`（项目内目录）。
   另外 vite dev server 运行时会占住该临时目录，构建前先停 dev server。
6. **PowerShell 控制台编码。** 默认 GBK，打印中文/希腊字母会 `UnicodeEncodeError` 或乱码。
   命令前加 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`；
   Python 脚本里 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`。
7. **`uvicorn.exe` 不存在。** venv 里没有 console script，必须 `python -m uvicorn`。
8. **pypdfium2 5.x API 变化。** `get_objects()` 返回生成器（不能 len）；对象类型是 int
   （1=text 2=path 3=image 5=form）；图像 `get_bounds()` 是像素坐标。
9. **MinerU 只能用 ASCII 路径 + 只能写工作区。** 与 Docling 同理，输入先复制到
   `MINERU_WORKDIR/input/`；子进程的 `TEMP/TMP` 也必须钉到工作区内，否则
   `PermissionError`（DSH 沙箱拒绝 `C:\mineru-work`、`%TEMP%`）。
10. **MinerU 安装踩坑（本机实测）。** PyPI 直连约 70KB/s；清华镜像当时缺 `mineru==4.2.0`；
    **pip 26.1.2 有 bug**（对镜像报 `from versions: none`），升级到 26.3 后恢复。
    最终可行路径：`pip download --no-deps -i https://pypi.org/simple mineru==4.2.0`
    先拿 wheel，再 `pip install <wheel> -i https://pypi.tuna.tsinghua.edu.cn/simple` 装依赖。
11. **MinerU flash 的输出结构跟 Docling 不一样。** 它不产独立 caption 块，图注/表题挂在
    `image/chart/table` 块的 `content` 子块里（`*_caption`）；图片 bbox 是归一化 [0,1]。
    适配器已处理，但改映射时要记得这两条，否则会「静默丢图注」。
12. **dev 库 schema 要手动跟上迁移。** SQLite 没有 alembic 版本表；加了 0003 之后，
    旧 `.data/dev.db` 必须先 `ALTER TABLE`（或删库重建），否则 worker persist 报
    `no such column: label_source`，而且 job 会 **failed 得很干净**（不静默，但容易误判成解析问题）。
13. **长驻进程不会热加载代码。** 改 `workers/run.py` / `labeling.py` / `ocr_cross.py` 后必须重启
    worker；改 `routers/figures.py` / `schemas.py` 后必须重启 API。否则会看到「代码改了、
    结果没变」——本轮在双 OCR 校核上踩过两次，重跑了一遍 5 本才发现。
14. **RapidOCR 默认模型是 PP-OCRv6（与 MinerU 同族）。** 为了独立性，第二套固定用
    **PP-OCRv4 mobile**（`RapidOCR(params={"Det.ocr_version": OCRVersion.PPOCRV4, ...})`）；
    首次调用会自动下载 v4 模型到 `site-packages/rapidocr/models`（约 15MB，需网络）。
    离线环境要提前下好，否则交叉校核会抛异常（worker 里会 warning 后保留原结果）。
15. **`agent-browser` 不要用于这个界面。** 页面有 800ms job 轮询，
    `agent-browser wait --load networkidle` 永远不返回，整个 CLI 会卡死。
    截图/交互验收统一用 headless Edge + CDP（`.data/tmp/cdp.py`），默认无窗口、不占桌面。

## 15. 关键决策记录（ADR-0001 摘要）

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 形态 | 自部署 Web 应用（否掉桌面壳） | 团队共享天然支持；部署体验即产品体验 |
| 许可证 | 混合：服务端 AGPL，schemas/mcp MIT | 服务端防闭源 SaaS；边缘换生态 |
| 复用 | MIT/Apache/BSD 直接依赖；AGPL/GPL 只走独立容器 | 换掉 PyMuPDF 后 AGPL 暴露面只剩 MinerU 一个容器 |
| 图表检索 | 三路（出处/语义/主题），不是单一列表 | 确定性检索不能退化成"相似的" |
| 图版本 | 图挂 `paper_version` 而非 `paper` | 预印本与正式版图号会变 |
| 误报 | 可接受，但必须有纠错通道 | 多智能体协作里 agent 是主纠错门限 |

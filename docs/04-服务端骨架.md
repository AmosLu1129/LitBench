## 检索怎么判路

不是「加个排序参数」，而是三条路各有各的实现：

| 输入命中 | mode | 行为 |
| --- | --- | --- |
| DOI / arXiv / citekey / 作者+年份 / 图号 | `provenance` | 精确匹配，0 条就是 0 条，不返回「相似结果」 |
| 只有自由文本 | `semantic` | 当前降级为 caption + 标题 ILIKE，响应带 `degraded: true` |
| 什么都没有 | `browse` | 按时间倒序浏览 |

一次查询可以同时带多种线索：`Wang 2019 Fig. 3` 会同时约束作者、年份、图号。

## 两个容易埋雷的点

1. **图号归一化里子图字母必须紧贴数字。**
   `Fig. 3a` 是子图，`Fig. 3 of ...` 不是。第一版正则允许空格，结果
   `"Fig. 3 of 10.1016/..."` 被解析成 `fig:3o`（把 `of` 的 o 当成了子图字母），
   出处检索直接查不到。已修，测试 `test_doi_plus_label` 守着这条。

2. **语义检索时，自由文本不能当标题过滤条件。**
   `Wang 2019` 这类查询里剩下的文本是标题片段，可以 AND 进去；
   但 `TG curves` 是语义查询，把它按标题 AND 过滤会让结果永远为 0。
   所以 `_paper_conditions` 只在 `provenance` 模式下把文本当过滤条件。

## 外部可选组件：OCR（不进主镜像）

扫描件（没有文字层）走 OCR，两条路径：

| 路径 | 依赖 | 形态 |
| --- | --- | --- |
| `OCR_BACKEND=docling` | 主镜像：`docling` + `rapidocr` + `onnxruntime`（MIT/Apache） | 进程内，`do_ocr=True` |
| `OCR_BACKEND=mineru` | **独立 venv**：`C:\mineru-env`（或容器）里的 `mineru-kit` CLI（AGPL） | **子进程**，主进程绝不 import |

MinerU 相关环境变量（见 `.env.example`）：

- `MINERU_CMD`：CLI 路径（默认 `C:\mineru-env\Scripts\mineru-kit.exe`）
- `MINERU_WORKDIR`：ASCII 工作目录（输入复制、输出 JSON、临时目录都在这；默认 `C:\litbench\.data\mineru-work`）
- `MINERU_HOME`：模型与配置目录（`config.yaml` 的 `model.base_dir` 指到 `.../models`）
- `MINERU_MODEL_SOURCE=modelscope`、`MINERU_TIER=flash|basic|standard|advanced`

> 两个环境坑：①MinerU / Docling 的解析层都打不开**非 ASCII 路径**，所以工作目录和 venv 都要放在 ASCII 路径下；
> ②DSH 会话里的子进程只能写工作区内路径，`C:\mineru-work` / `%TEMP%` 会被拒，所以工作目录放在 `C:\litbench\.data\` 下。

## 跑起来

```bash
cd server
python -m venv ../.venv
../.venv/Scripts/pip install -r requirements.txt pytest pytest-asyncio httpx aiosqlite
../.venv/Scripts/python -m pytest -q          # 21 passed
../.venv/Scripts/uvicorn litbench.main:app --reload
```

没装 Postgres 也能跑测试（SQLite），但 `uvicorn` 起服务需要 `DATABASE_URL`
指向一个真实库，并先 `alembic upgrade head`。

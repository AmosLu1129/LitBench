# Web 架构、数据模型与路线

## 1. 形态修订（v0.2）

原方案是「本地优先的桌面应用」。约束改为 **Web 版 + 开源 + 全领域 + 图表占比最高** 后：

- 主体形态：**自部署 Web 应用**（`docker compose up` 一条命令起全栈）。
- 优势变简单了：不再需要 Tauri 壳、不需要双端打包，团队共享天然支持。
- 代价：多用户隔离、上传/队列/长任务、以及「别人跑不起来」的部署体验。**部署体验就是这个项目的产品体验。**

## 2. 服务拓扑

```
浏览器 (React + PDF.js)
   │  tus 分片上传 / SSE 进度
   ▼
API (FastAPI) ──► Postgres (pgvector)  ◄── Worker: 解析 (Docling)
   │                                        └── 可选：MinerU 容器
   ├──► 对象存储 (PDF / 图 / 缩略图)
   ├──► MCP Server (只读)
   └──► 导出 (LaTeX / BibTeX)
```

`compose.yaml` 服务：`web` / `api` / `worker` / `postgres` / `valkey` /（可选）`mineru`。

关键工程点：

- **上传**：大 PDF 走 tus 分片，不要一次 POST。
- **进度**：SSE 推 job 进度，别轮询。
- **渲染**：浏览器 PDF.js 渲染 + 自定义 bbox overlay；服务端只给 block JSON，不给图片。
- **队列**：job 表 + Valkey；worker 幂等、可断点续跑。
- **LLM**：设置页配 base_url + key（BYO），支持 Ollama / vLLM；绝不内置 key。
- **多用户**：v1 单租户自部署，但表里先带 `user_id` / `workspace_id`。

## 3. 图表优先的五条设计决定

面向全领域、按「图表占比最高」准备，图/表必须是**一等公民**，不是文献的附件。

1. **图/表与文献平级**：独立 id、独立主题标签、独立检索入口。工作台默认是**双轴视图**——按文献分组（知道要找哪篇）与按主题平铺（不知道找哪篇），不是单一列表。
2. **不试图理解图的内容**：blot、XRD 谱、地质图、架构图、系统发育树，语义差异过大。主数据永远是 **图 + caption + 上下文段落 + 出处 + 许可提示**；VLM 描述只作可选辅助字段。
3. **矢量图按 bbox 渲染**：matplotlib 出的图在 PDF 里是几千条 path，抽 embedded image 只会得到碎片。按 figure bbox 以 2–3× DPI 渲染成位图。
4. **caption 远距离匹配**：跨栏、跨页极常见。用「版面距离 + 编号匹配（Fig. 3 / 表 2）」双策略，不要只靠相邻。
5. **表格分两类**：结构化（HTML/单元格）与图片型（扫描），后者走 OCR + 表格识别并标 `quality:image`，UI 上要能看出来。

## 4. 图表检索：两条路径，不是一个列表

「按主题浏览图表墙」和「按文献找某一幅图」是两个不同任务，混在一个列表里两边都难用。

| 路径 | 输入 | 检索方式 | 硬性要求 |
| --- | --- | --- | --- |
| 出处检索 | 标题 / 作者+年份 / DOI / arXiv / citekey /「Fig. 3」 | 结构化精确查找 | 毫秒级，不返回「相似结果」 |
| 语义发现 | 「哪些文献有第二个失重峰的 TG 曲线」 | BM25 + 向量 + 过滤 | 可排序、可解释 |
| 主题浏览 | 不输入，直接翻图表墙 | 按 figure_type / topic 分面 | 缩略图优先 |

**搜索框做 intent routing**（规则可解释、可调试）：

- 命中 DOI / arXiv / citekey / 「作者+年份」 → 出处路径
- 命中 `Fig 3` / `图3` / `表2` / `Figure 3a` → label 路径（可叠加文献约束）
- 其余 → 语义路径

### 三个必须做对的工程点

1. **label 归一化**：`Fig. 3` / `Figure 3` / `FIG.3` / `图3` / `Fig.3a` → `fig:3` / `fig:3a`。同时保留 `label_raw`，因为插引用时要显示原文写法（「Fig. 3」而不是「fig:3」）。
2. **文献别名索引**：标题、短标题、第一作者+年份、DOI、arXiv id、Zotero citekey。用户输 `Wang 2019` 的概率远高于完整标题。
3. **版本陷阱**：arXiv 版 Fig.3 ≠ 正式版 Fig.3（编号会变）。图必须挂在 `(paper_version, label)` 上，引用指向你实际读到的那一版。这是最容易埋雷的地方。

### UI

同一个搜索框，两个轴：

- **按文献分组**（树：文献 → 图/表）——「我知道要找哪篇」
- **按主题平铺**（墙）——「我不知道要找哪篇」

## 5. 数据模型

```sql
paper(id, user_id, doi, title, year, venue, authors_json, status)
paper_version(id, paper_id, kind, venue, year, doi, arxiv_id,
      file_sha256, page_count, parsed_at)
-- kind: preprint|published|correction —— 图编号会随版本变

block(id, paper_version_id, page, bbox_json, type, text, order_idx,
      parent_id, engine, conf)
-- type: text|title|section|table|figure|caption|formula|ref|header|footer

figure(id, paper_version_id, block_id, page, bbox_json, image_path,
       thumb_path, label_raw, label_norm, label_num, subfig_json,
       caption, figure_type, license_hint, cite_key)
-- figure_type: chart|micrograph|photo|map|diagram|structure|other
-- license_hint: reuse|permission|redraw|unknown
-- cite_key 形如 P0042v1-F3，MCP 与草稿引用都用它

tab(id, paper_version_id, block_id, page, html, cells_json, caption, quality)

card(id, paper_id, schema_id, schema_version, fields_json, model, prompt_hash)
card_field(card_id, key, value, evidence_block_ids JSON, conf)

claim(id, paper_id, text, polarity, conditions_json, evidence_block_ids JSON)

topic(id, parent_id, name)                    -- 受控词表
paper_topic(paper_id, topic_id, source, conf)
figure_topic(figure_id, topic_id, source, conf)

project(id, user_id, title, template_id, venue)
outline_node(id, project_id, parent_id, title, order_idx, claim_ids JSON)
draft(id, project_id, latex, updated_at)
cite_anchor(id, draft_id, sentence_hash, paper_id, block_ids JSON, verdict)

schema_pack(id, name, version, fields_yaml, extractor_prompt, compare_dims)
job(id, kind, paper_id, status, progress, error, attempts)
```

**不变量**：`card_field` / `claim` / `cite_anchor` 的 `evidence_block_ids` 非空才允许落库。这是「可溯源」的工程实现，不是提示词里的承诺。

**领域适配**：卡片字段不写死。用 `schema_pack`（YAML 定义字段 + 抽取提示 + 对比维度）实现全领域支持：内置 `general`，再随手做 3–4 个高频包，其余靠社区贡献。

## 6. 路线（复用后的修订版）

| 阶段 | 周期 | 产出 | 验收 |
| --- | --- | --- | --- |
| P0 复用验证 | 2 周 | Docling 跑通 20 篇 × 3 学科，MinerU 对照 | 图-caption 绑定 ≥80%、表格还原可用、决定可选档是否值得 |
| P1 Web 骨架 | 5 周 | 上传→队列→解析→block→PDF.js 高亮→图表双轴视图；`docker compose up` 起全栈 | 一台干净机器 10 分钟内跑起来并解析完一篇 |
| P2 写作侧 | 5 周 | 卡片/claim、对比矩阵、反向大纲、LaTeX 骨架 + `\cite` 占位、引用校验 | 10 篇 → 一份可编译的综述骨架，引用全部可回查 |
| P3 图表与分发 | 4 周 | 曲线上数字化、模板库、MCP、在线 demo、schema pack | 一套模板直接出 PDF；3 人课题组共用 |

约 16 周（一个人）。

## 7. 复用的真实代价

复用省掉的是「调模型、写解析器」，但工作量会转移到两处没人能替你做的地方：

- **归一化层**：Docling 的输出 schema、MinerU 的输出 schema、你自己的 block schema 三套对齐，是最脏最耗时的一块（约 2–3 周），必须配 golden test 防回归。
- **产品层**：双轴图表视图、出处检索、引用校验、对比矩阵、草稿工作流——开源世界里没有可抄的。

所以：复用让你省 40% 的代码量，项目总工作量大概只降 25%。**别指望「拼装开源项目」能把 18 个月变成 3 个月，它能把 18 个月变成 13 个月。**

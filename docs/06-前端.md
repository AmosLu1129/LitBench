# 前端：双轴图表工作台（P1）

## 运行

```bash
# 1. 解析样本文献，生成 SQLite 开发库（本机没有 Postgres 也能跑）
python scripts/seed_dev.py

# 2. 起 API（用同一个库）
cd server
set DATABASE_URL=sqlite+aiosqlite:///D:/path/to/lit-workbench/.data/dev.db
set STORAGE_DIR=D:\path\to\lit-workbench\.data
uvicorn litbench.main:app --port 8000

# 3. 起前端
cd web
npm install
npm run dev          # http://localhost:5173
```

`seed_dev.py` 跑完会把这三条命令直接打印出来。

## 界面结构

```
┌ 顶栏：品牌 + 搜索框 + 模式徽标 + 统计 ─────────────────────┐
├ 侧栏：文献列表（每篇的图数） ┬ 主区：图表网格 ──────────────┤
│                              │  点卡片 → 右侧详情面板       │
└──────────────────────────────┴──────────────────────────────┘
```

**两轴**：

- 点侧栏某篇文献 → 主区只显示这篇的图（**按文献**，知道要找哪篇时用）
- 点「全部图」/直接搜索 → 主区显示全部或检索结果（**按主题/内容**，不知道找哪篇时用）

## 上传与解析进度（2026-11-11 加）

入口在顶栏「上传 PDF」（`<input type="file">` 藏在 `<label>` 里，样式与顶栏按钮一致）。

流程：`POST /api/papers`（multipart）→ 立刻拿到 `job_id` → **每 800ms 轮询**
`GET /api/jobs/{id}` → `done` 后 `loadPapers()` + 一个 `refreshKey` 让当前视图（检索结果
或某篇的图）重新拉一遍。

进度条有 5 个状态，文案都写在 `UploadBar` 里：

| 状态 | 文案 |
| --- | --- |
| uploading | 正在上传 / 按钮变「上传中…」 |
| queued | 已排队，等 worker 取任务 |
| running | 解析中 42% |
| done | 解析完成，列表已刷新（去重时补一句「同一文件已在库中，按幂等重解析」） |
| failed | 解析失败：`job.error` 原文 |

**为什么先轮询不用 SSE**：解析一篇 15 页论文 2 秒，轮询足够；SSE 要多维护一条长连接和
断线重连。等按需升级 Docling（单篇 60 秒）之后再上 SSE 更划算，接口契约不变。

已知不足：一次只能传一个文件；不支持拖拽到页面。

## 三个界面状态（都用 Edge 无头截图验证过）

| 状态 | 表现 |
| --- | --- |
| 浏览 | 39 张图铺成网格，缩略图 + 图号 + 页码 + caption 摘要 |
| 出处命中 | 输入 `Figure 3` → 4 条，徽标显示「出处检索」（绿色） |
| 出处未命中 | 输入 `Figure 9` → 0 条 + 黄色提示条 + 解释性空状态 + 示例词 |
| 上传中 | 顶栏进度条「已排队，等 worker 取任务」/「解析中 42%」 |
| 上传完成 | 进度条变绿「解析完成，列表已刷新」，侧栏顶部出现新论文 |

查询写在 URL 里（`?q=Figure%203`），可分享、刷新可恢复。

## 详情面板

点卡片打开：大图、caption 全文、引用键 `cite_key`（可复制）、页码、许可提示。
许可提示是给「一键引用图表」铺路的——直接截图复用有版权风险，
界面明确引导到「引用建议」或「数据化重绘」。

## 原文查看器（bbox overlay）

点详情面板的「在原文中查看」→ 打开 PDF.js 渲染的原页，图区域用红框标出。
这是整个产品的**证据锚定**：用户必须能一眼确认「这张图确实在原文这一页的这个地方」。

- 深链：`?fig=<figure_id>` 直接打开到那一页（可分享、可刷新）
- 键盘：`←`/`→` 翻页，`Esc` 关闭
- 坐标：后端 bbox 是 PDF 点、左上原点；PDF.js viewport 同为左上原点，乘 scale 即可，不翻 y
- 高清屏按 `devicePixelRatio` 放大 canvas，避免框和图形错位

**拖框修正（2026-11-11 加）**：框得不对时，直接在页面上拖一个新框（蓝色虚线预览），
松手即 `POST /review {verdict:"wrong", bbox}`。后端按新框重裁缩略图，前端把 overlay、详情面板、
卡片网格一起刷新（`image_url` 带 `?v=` 破缓存）。坐标换算：CSS px ÷ `viewport.scale` = PDF 点，
再夹到页面范围；拖动用 pointer 事件 + `setPointerCapture`，拖出画布也不断。

**已知不足**：bbox 有时只覆盖图的一个子面板（比如一张四联图只框住了左下角）。
按产品设计这可以接受——多智能体协作里有一道纠错门限，而且现在人也能直接拖框改。
**overlay 是纠错通道的前提，不是终点。**

> 这条交互没有做浏览器自动化回归：agent-browser 在本机会把 headless Chrome 合成成一个
> 黑窗口、且偶发卡死。拖框本身的后端链路（review → 重裁 → 缓存失效）有测试覆盖
> （`server/tests/test_review_thumbnail.py`）。

## 已知问题（按严重程度）

1. ~~**约 15% 的缩略图是正文而不是图**~~ **2026-11-11 修复真因**：pdfium 的 bbox 是
   PDF 原生左下原点，而裁剪/overlay 按左上原点用，等于每张缩略图都从页面镜像位置裁。
   现在 parser 出口统一转换。剩余的误报是「页眉/正文细条混进上边界」这类边界问题，
   不再靠调阈值硬凑，走 review 通道 + Docling 增强档。
2. **caption 合并只解决了一部分。** 已经把 caption 的后续行按几何拼回去了（平均 82→94 字，
   最长 133 字），但行级解析遇到「图在 caption 下方」「caption 被拆成多个 block」时仍会断；
   同一批样本上 Docling 的 caption 平均 281–611 字，那是版面模型的优势，不是打补丁能追上的。
3. ~~修正 bbox 后缩略图不重渲染~~ **已修**：`POST /review` 带 bbox 时后端按新框重裁缩略图，
   并把 `image_url` 换成带 `?v=<reviewed_at>` 的版本（图片有 24h 缓存，不换 URL 会拿旧图）。
4. 文献标题目前是 `分类 · arXiv id`，没接真正的元数据（Crossref/arXiv API）。

## 实现取舍

- **没引 UI 框架**：整个界面 4 个组件、约 300 行 TSX + 400 行 CSS。
  桌面级工作台不需要组件库，自己写反而更快调版式。
- **不做乐观更新**：数据量小（几十张图），每次操作直接重查，少一类状态 bug。
- **图片走 `/api/figures/{id}/image`**，不由前端拼路径——路径约束在服务端，
  且这个接口带路径穿越校验（见 `server/tests/test_figure_image.py`）。
